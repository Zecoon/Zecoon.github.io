多机 Agentic GRPO 的基础设施踩坑记录

Created on November 01, 2026

2026   ·   rl   grpo   infra   verl   vllm   ·   tech

过去两周（10-20 → 11-01），我们在 4 台 8×A800 的机器上用 verl 给一个 Qwen3.5-4B 的医学搜索 agent 做 GRPO。agent 每道题要在「搜索 → 读网页 → 再搜索 → 作答」之间循环几十轮，单条轨迹最长到 256K token。这类 agentic RL 的难点很大一部分不在算法，而在基础设施：训练、推理、工具服务、外部 API 四套系统耦合在一起，任何一环出问题，最后都表现为「分数掉了」。

这篇只记录 infra 层面 的坑，算法和奖励设计不在这里。每条按「现象 → 原因 → 处理」写，⭐ 表示会静默出错、最值得警惕的那一类。

一页速查

起跑或续跑之前，我们现在会对着这张表过一遍：

检查项 防的是什么
各机器上的 latest_checkpointed_iteration.txt 取最大值，分片齐全 从错误步数续训 ⭐
续训后日志里 Resuming from …/global_step_N 的 N 对不对 同上 ⭐
任何提速 / 换引擎的配置，先过训推一致性（k3 KL）检查 推理引擎静默算错 ⭐
外部 API 用正常大小的请求测延迟，看账户余额而不是 key 额度 API 变慢 / 欠费被误判成模型退步 ⭐
上次的工具服务端口已释放 集群「起不来」
磁盘余量（每步每台约 25 GB） 存盘写爆

1. 推理引擎：吞吐测试看不出的错

⭐ KV cache CPU offload 在混合架构上算错

为了提速，我们试了 vLLM 的 native KV CPU offload。吞吐测试一切正常，但训练端和推理端的 k3 KL 从正常的 ~0.0003 涨到 0.005–0.05，个别 token 的概率差到 1.0，得分随之下降。

原因是 Qwen3.5 是 GDN（线性注意力）+ 全注意力的混合模型，offload 读回的递归状态不对。纯吞吐 benchmark 完全发现不了这种错，因为它只看速度不看输出。

教训：任何改变推理路径的提速手段，进正式 RL 前都要先做训推一致性检查。我们现在固定用一个 k3 KL 脚本把关，KL 回到 ~0.0003 量级才放行。

并发塌方区

每卡在途 15 条轨迹时，前缀缓存命中率只有 19%；降到 8 条，命中率回到 94%，单位时间完成的轮次反而是前者的 3 倍。原因是 15 条 × 约 10 万 token 超过了 KV 容量，轨迹在等工具返回时前缀被挤出去，下一轮只能整段重算。agentic rollout 的并发不是越高越好，要按「在途 token 总量 ≤ KV 容量」来定。

⭐ 基座缺 generation_config.json，SGLang 不停

在 SGLang 上，模型每轮生成都不停下：平均 25 次工具调用里只有 8 次真正返回。原因是 HF 上的 Qwen3.5-4B 基座没有 generation_config.json，config.json 里的 eos 只有 <|endoftext|>；vLLM 会用 tokenizer 里的 <|im_end|> 所以没事，SGLang 不会。补上 generation_config.json（两个 eos）就好了。

SGLang 的其他几个坑

  • GDN 状态缓存默认预留过大（575 条 / 27 GB），KV 只剩 vLLM 的 57%，没压力时也慢 25%。手动调小到 96 条。
  • 和 expandable_segments 冲突，启动即崩，用 SGLang 时要 unset PYTORCH_CUDA_ALLOC_CONF。
  • colocate 模式下 sleep 崩：训练前要让推理引擎释放显存，但还有在途请求。改成先 pause（abort 在途请求）→ 等 2 s → 释放 → 再 continue。
  • HiCache 主存占用约为设定值的 2 倍，且设定值必须大于 GPU KV 池，8 卡要超过 1 TB 内存才有效，最后放弃。

最终我们在做完引擎对比之后选了 vLLM。

2. 分布式训练框架

  • 一条坏消息杀死整个数据线程。 TransferQueue 的存储单元收到一条坏的 msgpack 消息，反序列化在 try 外面，于是工作线程直接退出，之后所有 put 都 200 s 超时，最后在别的地方报一个毫不相干的 KeyError。打补丁让它记录来源后丢弃坏消息，线程不死。
  • clip_grad_norm 的 all_reduce 偶发挂死。 32 个 rank 全部卡住 1 小时以上，nccl_timeout 也没生效。根因没查到，只出现过一次；我们加了看门狗：进度 60 分钟不动就存下各 rank 的调用栈、杀掉、自动续跑。
  • 每步的长尾。 一步 2 小时，生成占 75%；前 60 分钟只完成了 37/96 组，剩下的时间都在等少数超长轨迹。加了单条轨迹 30 分钟硬超时（取消请求并终止推理，排队时间不计），超时 / 超长的轨迹 mask 掉不进梯度，再配合更小的 batch，一步降到约 46 分钟。

3. 存盘与续训：最危险的一类

⭐ 续训从错误的步开始

这是这次最惊险的一个。第 40 步跑完后自动续训，日志却写着 Resuming from global_step_18。巡检时发现，第 19 步刚开始生成、还没存盘。再晚约 40 分钟，它就会覆盖 global_step_19，接着滚动删除会把 19–40 步逐个删掉，两天的训练白跑。

原因：latest_checkpointed_iteration.txt 只写在 driver 所在的那台机器上，而 driver 每次可能落在不同的机器。续训脚本的第一版无脑把另一台的元数据同步过来，把 40 盖回了 18。更糟的是 rsync -a 保留了旧时间戳，文件看起来「没动过」。

现在的续训脚本：各机器的 latest 取最大值 → 核对该步各机分片齐全 → 缺的文件从另一台补 → 把步号写回所有机器 → 起跑后读日志里的 Resuming from，步号不对立即停训。

滚动删除只删了一半

开了「只保留最近 3 个 checkpoint」之后，一台机器上的旧步只剩 data.pt，另一台上 26 GB 的分片还在。原因是删除逻辑只在 rank 0 的 worker 里执行，其他机器上的分片永远不删；而且它只删本次进程存过的步。我们加了一个镜像清理脚本：主机删了哪一步，其他机器跟着删。

其他

  • 磁盘： 每步每台约 25 GB（模型 + 优化器状态），60 步要 1.5 TB/台。滚动只留 3 步，再每 10 步用 cp -al 硬链接一份里程碑：不占额外空间，滚动删除也删不掉。
  • EPOCHS=1 让训练第 5 步就「正常结束」：80 题 / batch 16 正好 5 步一轮，上层脚本的默认值覆盖了下层设定。步数应该只由 total_training_steps 决定。
  • 停训会丢半步：只有步末才存盘，停在中间这一步约 46 分钟的生成全部作废。叫停前先等 latest 文件变化。
  • 合并 HF 权重前，分片要先汇到一台机器上，因为分片按节点本地存储。

4. 工具服务

  • 端口没释放导致「Ray 起不来」：上次停训时工具服务没杀干净，新服务看到端口被占就直接跳过。续训脚本现在先 kill，再循环等端口真正释放。
  • listen backlog 默认只有 5：64 并发时 connection reset，改成 4096。
  • 沙箱 podman rm -f 每次干等 10 s：它先发 SIGTERM 等超时，改用 podman kill（0.4 s）。
  • 搜索缓存的键归一化：小写、去标点、词排序后命中率 50–56%。我们模拟过更激进的放宽：Jaccard ≥ 0.8 能再省 25%，但会把不同问题的答案混在一起，不建议。

5. 外部 API：最容易被误判成「模型退步」

⭐ 中转 API 间歇变慢

网页摘要和判分都走同一个第三方 LLM 中转 API。两周里它出现过三次间歇性变慢，单次请求从几秒涨到几十秒，读网页的工具调用超时率随之上升，正确率曲线明显下凹，看起来完全像模型退步。

这个无法根治，只能靠盯：

  • 巡检时看工具调用耗时的中位数和 p90，并用极小请求单独测中转延迟；
  • 统计时除了整体正确率，也看「作答者正确率」（只算没超时、给出答案的轨迹），把 infra 因素剥离出来；
  • 受污染的步在曲线上用灰底标出来。

⭐ 余额看错

有一次 API 返回 403 quota not enough，摘要失败率从 5% 跳到 50%，判分无限重试，吞吐跌到零。之前查余额时显示还有钱，但那是 key 的额度，不是账户钱包；而且用 “say ok” 这种小请求测试时还能通过，掩盖了问题。

搜索额度耗尽

某天早上开始搜索全部失败，验证集全 0 分。原因很朴素：搜索 API 额度用完了。之后我们让网关的 key 池支持热加载，改配置文件即生效，并把余额检查加进起跑前的清单。

6. 集群与运维

  • 机器间时钟差约 7 分钟，跨机对比日志时间时要注意。
  • 不要原地修改正在运行的 bash 脚本。 bash 是边读边执行的，原地改会让正在跑的脚本读到错位的内容。先停，再改，再起。
  • 字符串替换会静默失败。 一次把目标步数从 200 改成 100，控制步数的那一行模式没匹配上，仍然是 200，核对时才发现。改完脚本一定 grep 一遍关键参数。
  • pkill -f 会杀到自己。 模式串出现在自己所在的 bash -c / ssh 命令行里，命令执行到一半就被杀了。用 pid，或者写成 [x]yz 的形式。

7. 统计与监控

  • ⭐ 半截步的轨迹混进统计。 停训或误续训时，做了一半的那一步也会写轨迹日志，步号和之后重跑的同一步相同，于是某一步出现了 253 条轨迹（应为 128），输出 token 统计翻倍。画图脚本里现在维护一张「丢弃表」（续训时刻 + 步号 + 时间窗），每次停训都追加一条。
  • 单步分数波动大。 每步只有 16 道题，前后两步不是同一批题，续训后第一步比上一步低不代表没续上。要按整轮或同题配对比较。
  • 「日志不更新 = 挂了」经常是误报。 参数更新阶段约 13 分钟不打日志，等长尾轨迹又是 10–20 分钟。看 GPU 利用率和 pending 计数，超过 45 分钟不写再查。
  • matplotlib 中文字体全是方框：系统里的 Noto CJK 只注册出了 JP 字体，显式 addfont 思源黑体 CN 解决。

小结

回头看，最值得记住的是三类静默错误：

  1. 推理引擎算错但不报错（KV offload）：用训推 KL 把关，不要只看吞吐。
  2. 存盘 / 续训的元数据只在一台机器上：续训前取最大值、核对分片，起跑后再核对一次。
  3. 外部依赖变慢或欠费，表现为分数下降：监控工具耗时，把 infra 因素从模型表现里剥离。

agentic RL 的训练曲线是模型、引擎、工具、外部 API 共同作用的结果。在相信一条曲线之前，先确认它画的确实是模型。
